# PiperX 普通遥操与 Web 联合运行设计

## 目标

在 `.166` 上用一个独立于 EvoStudio 的进程完成左右两组 PiperX 主从遥操，
同时将两台从臂的同一份 CAN 反馈送入现有力矩估计与 Web 仪表盘。控制和监控
不得为同一从臂创建两套 CAN 接收生命周期。

## 已确认的问题

原 Web 监控为每台从臂各打开一个 SocketCAN raw socket。EvoStudio 随后启动
PiperX 时会对四个接口执行 `down -> bitrate 1 Mbps -> up`，导致已存在的监控
接收生命周期与控制启动发生竞争。原启动器还通过 `conda run` 间接启动服务，
SSH 关闭后远端 Python 可能成为孤儿进程。

## 架构

新建一个联合运行时，每台机械臂只打开一个 SocketCAN socket：

- 左主臂：`0040002C4148570C20343133`（当前 `can0`）；
- 左从臂：`004B00204148570D20343133`（当前 `can2`）；
- 右主臂：`003900454148571320343133`（当前 `can1`）；
- 右从臂：`003F002D4148571320343133`（当前 `can3`）。

主臂 socket 接收 `0x155..0x157` 和 `0x159` 控制帧。联合运行时把关节目标
转发到对应从臂，并将夹爪 effort 固定为 `1000`。从臂 socket 同时负责发送这些
控制帧、接收反馈，并将反馈帧直接交给 `PiperStateAssembler`、外力矩估计器和
SSE 发布器。因此 Web 不再额外监听 can2/can3。

运行时不执行 `ip link down/up`。它只按 USB-CAN 序列号解析接口，并在接口不为
UP 或比特率不正确时失败退出，避免在线重置现有 CAN 总线。

## 安全与生命周期

启动器首先检查 EvoStudio `/client/status` 必须为 `idle`，然后停止
`evostudio-client` systemd 服务。联合进程退出后，在同一个可见 SSH 会话中
恢复该服务。用户可能被 SSH/sudo 请求输入凭据，仓库不保存密码。

联合进程启动时：

1. 解析并核对四个不同的 USB-CAN 序列号；
2. 打开四个 socket，并查询/验证固件至少为 `S-V1.8-9`；
3. 只向主臂发送示教输入角色 `0xFA`，绝不临时发送 `0xFC`；从臂切换为运动输出臂；
4. 直接读取主臂控制帧与从臂反馈，任一关节差超过 15 度或夹爪差超过 10 mm 时拒绝使能；
5. 从臂进入关节控制模式，确认六轴使能后才开始转发；
6. 主臂控制帧超过 250 ms 未更新时停止发送新目标并保持最后姿态；超过 1 s
   则运行时失败退出，不发送失能命令，避免机械臂突然失去支撑。

正常退出保持主臂为示教输入角色、从臂为运动输出角色，不主动失能机械臂。
控制线程或 Web 线程任一失败都会使整个进程退出，不能留下仅控制或仅监控的
半运行状态。远端直接执行 Evo-RL 环境的 Python，不再使用 `conda run`。

## Web 语义

沿用现有界面、SSE schema 和估计器。联合模式增加明确的运行模式字段，页面把
底部状态从“无 / RX ONLY”改为“普通遥操 / CONTROL + MONITOR”。当前标定范围
以外仍显示 `outside_calibrated_workspace`，不会为了显示曲线而放宽有效性门限。

## 测试与实机验收

纯单元测试覆盖帧转发、夹爪 effort 重写、初始对齐门限、主臂看门狗、一个
socket 同时供控制和估计、停止传播以及重复序列号拒绝。实机验收只在确认
EvoStudio idle 后进行：先保持主臂静止启动，检查 Web 更新；再由现场用户进行
小幅低速动作，确认左右从臂跟随、Web q/qd/current 同步、can2/can3 无新增
rx_dropped。退出后确认联合进程和 18765 端口消失，并恢复 EvoStudio 服务。
